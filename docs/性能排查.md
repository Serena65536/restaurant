# 性能问题排查记录（2026-11-05）

## 第二轮：上传图片仍然很慢 / 传不上去（真正的 bug）

用工作区里的两张样图复现：

| 文件 | 尺寸 | 大小 |
|---|---|---|
| `share_1793894205908.jpeg` | 1280×852 | 470 KB |
| `share_1793894214434.jpeg` | 1200×774 | 92 KB |

本机上传 470KB 的那张，接口返回：

```json
{"url":"/uploads/xxx.jpg","size":481280,"compressed":false}
```

`size` 等于原图、`compressed=false` —— **服务端压缩从来没生效过**。服务端日志反复打印：

```
[upload] 压缩失败，保留原图： Cannot use same file for input and output
```

原因是 multer 按 MIME 给 JPEG 起名 `xxx.jpg`，而我要输出的目标文件也叫 `xxx.jpg`——同一个路径。sharp 不允许输入输出同名，于是直接抛错；catch 分支又「保留原图」，结果每次上传都是原图落盘。PNG 上传反而正常（扩展名不同），所以之前用小图测试时看不出来。

### 修复

1. sharp 先写到 `xxx.opt.jpg`，成功后 `rename` 覆盖，再删原文件；
2. `compressed` 改成独立的布尔值，不再靠文件名比较；
3. App 端上传从 `fetch` 换成 `XMLHttpRequest`：能显示**上传百分比**，并有 90 秒硬超时和明确的失败提示（以前是无限转圈，看不出来在传还是死了）。

### 修复后实测

| 场景 | 前 | 后 |
|---|---|---|
| 服务端落盘（470KB 原图） | 470 KB | **102 KB** |
| 手机端压到 800px 后上传 | 470 KB，隧道 22 s | 70 KB，**3.4 s** | 
| 落盘大小（70KB 上传） | 70 KB（未压） | 75 KB（q78 重编码） |
| 上传失败表现 | 无限转圈 | 进度百分比 + 90s 超时提示 |

## 第一轮：整体操作慢

## 现象

「每个操作都要加载很久，尤其是上传或修改菜品图片的时候」。用户确认网络本身没问题（挂了代理，浏览器访问正常）。

## 实测数据（改之前）

| 项目 | 数值 |
|---|---|
| 本机接口响应 | 2–16 ms |
| 公网隧道单次请求 | 0.7–5 s |
| 隧道吞吐 | **约 15 KB/s** |
| 菜品图单张 | **1326–1371 KB**（手机原图直传） |
| 点餐页首屏图片总量 | **3.97 MB** |
| 上传一张图 | 1.3 MB 走 15KB/s ≈ **90 秒** |
| 店主首页 | 每次 3 个请求（分区 / 概况 / 订单） |

## 根因（按影响排序）

1. **图片没压缩**：`react-native-image-picker` 只在需要缩放时才重新编码，手机截图/原图宽度小于 limit 时原样返回，1.3MB 的 PNG 直接上传、直接当菜单图下载。点餐页一次要拉 4 MB。
2. **上传的是原图**：1.3MB 走十几 KB/s 的链路，几十秒起步。
3. **店主首页每次 3 个请求**：隧道下每个往返 1–3 秒，叠加起来就是「点一下等半天」。
4. **隧道链路本身慢**：cloudflared 连到了洛杉矶边缘节点（`location=lax13`），本机到那边只有 ~15KB/s。这台机器有系统代理 `127.0.0.1:7890`，但 cloudflared 不读 Windows 系统代理，直连出去就绕远了。

## 已做的修改

| 改动 | 位置 | 效果 |
|---|---|---|
| 选图时压到 800px / 质量 0.6 | `DishEditScreen.tsx` | 上传体积 ~1.3MB → ~80KB |
| 服务端用 sharp 统一转 900px JPEG | `admin.mjs` | 兜底保证存下来的图都很小（实测 1371KB → 82KB） |
| 存量图片批量压缩 + 改数据库引用 | `scripts/optimize-uploads.mjs` | 4 张图共省 4.98 MB |
| 图片缓存 30 天 immutable | `app.mjs` | 手机只下载第一次 |
| 店主首页合并成一个接口 | `GET /api/admin/dashboard` | 3 个请求 → 1 个 |
| 菜单内存缓存 | `api.ts` + `MenuScreen` | 回到点餐页立刻显示，后台再刷新 |
| 后端监听 0.0.0.0 | `index.mjs` | 同一 WiFi 可用 `http://电脑IP:8080` 直连（更快） |

## 改之后

- 点餐页图片总量：**3.97 MB → 约 250 KB**（16 倍）
- 单张菜品图：**1.35 MB → 82 KB**
- 上传一张图：**1.3 MB → 约 80 KB**，快到原来的十几倍
- 店主首页：3 次往返 → 1 次

## 仍存在的问题（不在程序里）

本机到 Cloudflare 边缘只有 ~15 KB/s（`location=lax13`）。这是链路问题，程序改不动。三个可选解法：

1. **同一 WiFi 用局域网地址**：`http://电脑IP:8080`（后端已监听 0.0.0.0；若连不上，需要给 node 放行 8080 入站防火墙规则）
2. 让 cloudflared 走代理：`--protocol http2 --proxy-address 127.0.0.1 --proxy-port 7890`（实测边缘节点仍是 lax，吞吐没改善，因为代理出口也在美国）
3. 换 ngrok / 自建 frp 等其它隧道
